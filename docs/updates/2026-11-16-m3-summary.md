# Milestone 3 summary (2026-11-16)

Milestone 3 (the event backbone) is done and CI is green on both commits: [run 43857220697](https://github.com/ynitin2004/LedgerGuard/actions/runs/43857220697) and [run 43857618594](https://github.com/ynitin2004/LedgerGuard/actions/runs/43857618594).

The five scaling gaps are now in M6 as proposed ADR-026 to ADR-030, each to be proven with a load test first: PgBouncer connection pooling, monthly table partitioning, read replicas, autoscaling on consumer lag, and an explicit "no sharding or multi-region" decision.

## What Milestone 3 adds
Every payment decision now also produces an event, written in the same database transaction as the payment. A publisher sends these events to Redpanda (the Kafka-compatible broker). The feature-updater consumer processes each event exactly once, even though delivery can repeat. Failed events go to a retry topic with increasing delays, then to a dead-letter queue (DLQ) that can be replayed. Consumer lag and unsent-event backlog are reported as metrics, and a `reconcile` command checks that the counts match end to end.

## Acceptance criteria, all met
- **Publisher killed mid-batch under load, on real Redpanda:** no events lost, the re-sent duplicates were absorbed, and the test asserts the exact counts (`tests/integration/test_kafka_pipeline.py`).
- **Chaos drill on the full local stack:** the publisher and then the consumer were force-killed during a 200 requests/second load. The payment API saw 0 errors, and **36,002 events reconciled exactly**: all published, all processed once, none dead-lettered.
- **Lag is visible** as a metric per partition (`ledgerguard_consumer_lag`).

## Problems found and fixed
- **The consumer couldn't keep up:** at first it processed 80–160 events/s while 200/s arrived, so it would have fallen further behind under sustained load. It now processes up to 200 events per database transaction, with one offset commit per batch: **754 events/s with one copy, and 1,419 events/s with three**.
- **A 30-second stall after a consumer was killed:** Kafka waited 45 s by default before handing its work to another copy. This is now about 10 s.
- **Hidden test failure on Windows:** a failed numpy import left half a numpy loaded in memory, which broke 11 property tests in the same run. The check now runs in a separate process.
- **The dev PC's security policy is inconsistent:** the Kafka client and numpy were blocked in the morning and loaded in the afternoon, while scikit-learn stayed blocked. `./scripts/dev.ps1 test-linux` runs the complete suite in a Linux container: **130 passed**. Windows gives 129 passed, with the scikit-learn test skipped.
